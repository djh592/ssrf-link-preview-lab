How Is the Testbed Designed?

Isolate every target

Redirect, DNS, and internal-report services are synthetic fixtures in a bounded Docker environment.

Safe and repeatable attacks

Vary only the policy

All five defenses use the same redirect handling, preview parser, and PycURL transport.

Like-for-like comparison

Observe both ends

Trial IDs join policy decisions and connected peers with independent destination-service events.

Evidence beyond the preview

The Web UI is a live view of the same instrumented testbed used in our experiments.

Earlier, I introduced the testbed as one of our contributions. Here are three design choices that make its experiments safe and comparable. [Click] First, every attack target is synthetic and runs inside a bounded Docker environment. We can therefore repeat the attacks without touching any real private service. [Click] Second, only the defense policy changes. All five policies use the same redirect handling, preview parser, and PycURL transport. This means that any difference in the results comes from the policy, not from a different implementation. [Click] Third, we observe both ends of every request. The preview service records its policy decision and connected peer, while the destination service independently records whether the request arrived. A trial ID joins these records together. This allows us to verify what actually happened, instead of trusting only what appears in the preview. [Click] The Web UI is not a separate simulation. It is a live view of the same testbed that we use for the experiments.
