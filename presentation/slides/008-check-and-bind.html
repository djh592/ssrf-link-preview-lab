Key insight | One security invariant

Every Connection Must Follow Its Destination Check

01

New URL, new decision

A redirect creates a new request. Check its destination before following it.

URL A→Redirect to URL B→Check URL B
02

Approved IP, same connection

DNS answers can change. Connect to the IP that passed the check.

Check IP A→Bind IP A→Connect to IP A

Validation must constrain the connection that follows.

A destination check only protects a request if it constrains where the service actually connects. Consider a request to URL A that returns a redirect to URL B. Approval of A says nothing about B, so we check the new target before sending the next request. Even when a hostname is checked for that hop, a later DNS answer can be different. If IP A passes the check, we bind the connection to IP A. In our implementation, manual redirects return each Location to the policy and libcurl's CURLOPT_RESOLVE supplies the approved IP while retaining the hostname. Peer recording is evidence after a request, not a preventive step.
