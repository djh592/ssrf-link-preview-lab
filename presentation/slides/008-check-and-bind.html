Key insight | One security invariant

Every Connection Must Follow Its Destination Check

01

New URL, new decision

A redirect creates a new request. Check its destination before following it.

URL A→Redirect to URL B→Check URL B
02

Approved IP, same connection

DNS answers can change. Connect to the IP that passed the check.

Check IP A→Bind IP A→Connect to IP A

Validation must constrain the connection that follows.

From our threat model, we get one central principle: a destination check must control the connection that follows. [Click] First, every new URL needs a new decision. If URL A redirects to URL B, approving URL A tells us nothing about URL B. We must check URL B before following the redirect. [Click] Second, the connection must use the exact IP address that passed the check. If IP A is approved, we bind the request to IP A instead of resolving the hostname again during the connection. In our implementation, we pass this checked IP directly to libcurl. Together, these two rules form our Check and Bind policy: check every new URL, and bind every connection to the approved IP. [Click] The general lesson is simple: validation must constrain execution. A destination is not protected if the final connection can ignore the earlier check.
